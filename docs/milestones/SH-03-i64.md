# SH-03 i64 対応

状態: 完了。前提: [SH-02](SH-02-typed-ir.md)。次: [SH-04](SH-04-floating-point.md)。

## 目的・変更対象

i64 の値を decode、検証、生成コード、ホスト関数の境界で保持する。対象は Reader、数値演算の生成、memory/global の値処理、関数の生成署名と差分テストである。

## 実施手順

1. 64 bit の LEB128 を追加し、最終バイトの符号・余剰ビット・切り詰められた入力を検証する。整数値を途中で32 bitへ縮めない。
2. i64 の定数、算術、比較、bit 演算、shift、rotate、bit count と i32 との整数変換を実装する。符号付き・符号なしの解釈を区別し、wrap する演算は C# の checked 設定に依存させない。
3. i64 の local、引数・結果、global、関数 import/export と、各幅の load/store を通す。所有 memory の範囲検査は既存の方針を維持する。
4. SH-01 で必要と判明した整数の符号拡張命令も追加する。全 MVP i64 演算と追加命令の対応表を記録する。
5. 公式 i64 テストと固定 seed の差分テストを追加する。Node.js との受け渡しでは BigInt と十進文字列またはビット列を使用する。

## 検証

[共通回帰とパッケージ検証](../self-hosting-design.md) に次のケースを登録する。

- 0、±1、符号付き最小・最大、全 bit が1の値、32 bit境界、2の53乗を超える値。
- shift の量が63、64、65、負の bit pattern となる場合。
- 符号付き除算の overflow、除数0、最小値を -1 で割った剰余。
- 符号拡張 load、unaligned access、末尾を越える load/store、global の初期化と変更。
- 型付きホスト関数を通る i64 の往復。checked な生成 C# と参照 WASM の一致。

## 合格条件

- [x] 全 MVP i64 演算と、対象 runtime に必要な追加整数命令のテストが通る。
- [x] i64 の import/export、memory、global を介して値が保存される。
- [x] JSON の number への変換で精度を失うテスト経路がない。
- [x] 対象一覧の i64 項目に実装とテストへの参照がある。

## 非対象・失敗時の扱い

memory64、SIMD、浮動小数点変換はこの段階では追加しない。i64 を実装しても memory のアドレス幅を64 bitに変更しない。

## 命令対応表と実装結果

整数に閉じた MVP 命令、整数間の変換、符号拡張の計49命令を追加した。`i64.eqz` と比較命令は i32 を返し、bit count と shift の値・量は i64 として検証する。定数と global 初期値は型と64 bit のビット列を保持し、生成コードでは `long` と明示的な `unchecked` を使う。符号付き最小値を -1 で割る場合は、除算を overflow trap、剰余を0として扱う。

| opcode | 命令 | 実装・検証 |
|---|---|---|
| `0x42` | `i64.const` | `Reader.SignedI64`、30件の定数・padded LEB と138件の不正 LEB |
| `0x50` | `i64.eqz` | `I64Operations`、公式 i64 と固定 seed 差分テスト |
| `0x51`–`0x5a` | `i64.eq/ne/lt_s/lt_u/gt_s/gt_u/le_s/le_u/ge_s/ge_u` | 同上。結果型は i32 |
| `0x79`–`0x7b` | `i64.clz/ctz/popcnt` | 同上。結果型は i64 |
| `0x7c`–`0x82` | `i64.add/sub/mul/div_s/div_u/rem_s/rem_u` | 同上。wrap、ゼロ除算、符号付き overflow を含む |
| `0x83`–`0x8a` | `i64.and/or/xor/shl/shr_s/shr_u/rotl/rotr` | 同上。shift 量の下位6 bit を使用 |
| `0xa7`、`0xac`–`0xad` | `i32.wrap_i64`、`i64.extend_i32_s/extend_i32_u` | `I64Operations`、固定 seed 差分テスト |
| `0xc0`–`0xc1` | `i32.extend8_s/extend16_s` | `I32Operations`、固定 seed 差分テスト |
| `0xc2`–`0xc4` | `i64.extend8_s/extend16_s/extend32_s` | `I64Operations`、固定 seed 差分テスト |
| `0x29`、`0x30`–`0x35` | `i64.load/load8_s/load8_u/load16_s/load16_u/load32_s/load32_u` | `MemoryOperations`、メモリ fixture と差分テスト |
| `0x37`、`0x3c`–`0x3e` | `i64.store/store8/store16/store32` | 同上。範囲検査を全幅に対して行ってから書き込む |

[機械可読の対応表](../self-hosting/SH-03-integer-coverage.json) には、各命令の署名、SH-01 での出現数と最初の関数・offset、実装ファイルとテストを記録した。SH-01 の対象 bundle は `10e2f5cee5fecd86681ef9e043082a04df131a0d7eb76855ac895ea0cbf3c9e6`。その中の追加符号拡張命令は `i32.extend8_s` が262箇所、`i32.extend16_s` が151箇所、`i64.extend32_s` が5箇所である。

この表の「実装済み」は小型 fixture での検証を指し、生成 runtime 全体の実行はまだ検証していない。同じ inventory にある `i64.trunc_f32_s/u`、`i64.trunc_f64_s/u`、`i64.reinterpret_f64` は [SH-04](SH-04-floating-point.md) に割り当て、未対応命令として診断する。整数規則と LEB の根拠は [数値命令の仕様](https://webassembly.github.io/spec/core/exec/numerics.html) と [バイナリ値の仕様](https://webassembly.github.io/spec/core/binary/values.html) による。
