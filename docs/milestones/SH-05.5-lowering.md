# SH-05.5 意味保存 lowering とターゲット別 backend

状態: 実施中。前提: [SH-05](SH-05-memory-data.md)。次: [SH-06](SH-06-tables.md)。profile 境界と netstandard2.1 memory lowering の初期実装を完了し、canonical IR の拡張と vector backend が未完了。

## 目的・位置づけ

現在の C# 生成は、検証済みの stack-machine 命令を `Pop`／`Push` と一時変数へ逐次的に写している。数値命令の C# 式、メモリアクセス、制御フローの出力が同じ emitter に集まり、対象 framework やライブラリに応じた実装を選ぶ境界がない。この段階では、検証済みの型付き IR と C# のソース文字列の間に lowering 層を置く。

lowering は WebAssembly の意味を保存した canonical 表現を作り、backend はその表現を対象ごとの BCL、intrinsics、ライブラリ型へ変換する。生成コードの target profile は明示的に選択し、実行環境の反射や実行時コンパイルで切り替えない。

SH-05.5 が扱うのはスカラー命令、メモリアクセス、backend 選択の基盤である。SH-06／SH-07 の table・例外を含む制御フロー全体の最適化と、大規模 module の分割は SH-08 で扱う。WebAssembly SIMD の全命令をこの段階の合格条件にはしないが、後続の `v128` lowering を .NET と Unity で別の型へ写せるインターフェースをここで定める。

## target profile

target profile は、生成コードが参照できる assembly、利用可能な型、意味保存のために許される lowering、fallback の規則を一組にした設定である。profile の選択は CLI、Source Generator、Unity の入力設定で同じ値を渡す。

| profile | 主な API | 用途 | 制約 |
|---|---|---|---|
| `portable-netstandard2.0` | 既存の C# 演算と内部 helper | 既存利用者と Unity の最小依存 | 最適化された BCL／SIMD API を参照しない |
| `dotnet-netstandard2.1` | `Span<T>`、`ReadOnlySpan<T>`、`MemoryMarshal` など | .NET でのメモリアクセスと buffer 処理 | 生成物と runtime の reference assembly を netstandard2.1 として検証する |
| `dotnet-vector` | 対象 framework が提供する `Vector128<T>` など | .NET 向けの SIMD lowering | `Vector128<T>` の利用可否を netstandard2.1 と同一視せず、target framework で固定する |
| `unity-mathematics` | `Unity.Mathematics.float4` など | Unity 向けのベクトル lowering | Unity package と IL2CPP でコンパイル・実行できる型だけを使用する |

`dotnet-netstandard2.1` は `Span<T>` と `MemoryMarshal` を積極的に使う profile とする。ただし、これだけで `Vector128<T>` が利用できるとは扱わない。SIMD profile は `System.Runtime.Intrinsics` を提供する target framework と reference assembly を別に固定する。

Unity profile は .NET profile の生成結果を流用しない。`Unity.Mathematics.float4` と .NET のベクトル型は lane 数や API が似ていても同じ型ではなく、各 backend が同じ canonical 操作を自分の型へ変換する。

生成器本体と既存の portable backend は、可能な限り .NET Standard 2.0 の依存を維持する。`Span<T>` などが必要な runtime／生成物だけを netstandard2.1 以降の profile として分け、portable profile に新しい assembly 参照を混入させない。target-specific runtime を multi-target にするか別 assembly にするかは、reference assembly と Unity package の依存関係を確認して決める。

対象ファイルは、既存の [Transpiler.cs](../../src/Wasm2Cs/Transpiler.cs)、[Module.cs](../../src/Wasm2Cs/Module.cs)、[Validator.cs](../../src/Wasm2Cs/Validator.cs)、[CSharpEmitter.cs](../../src/Wasm2Cs/CSharpEmitter.cs)、`I32Operations.cs`、`I64Operations.cs`、`FloatOperations.cs`、`MemoryOperations.cs` と、新設する canonical IR／profile／backend の実装である。profile の入力は [WasmGenerator.cs](../../src/Wasm2Cs.Generator/WasmGenerator.cs)、[Wasm2Cs.targets](../../build/Wasm2Cs.targets)、Unity の `WasmAssetBridge.cs` と各 asmdef へ同じ規則で接続する。

## lowering の構成

処理段階を次のように分ける。

```text
WASM binary
  → decode／型検証済み Module
  → canonical lowering（型・trap・little-endian を保持）
  → target backend（BCL／Vector128／Unity.Mathematics）
  → C# 構文・source emission
```

canonical lowering は、少なくとも次の情報を失わない。

- 値型、signed／unsigned の解釈、wrap と trap の区別
- f32／f64 の丸め、NaN、signed zero、reinterpret のビット列
- memory の範囲検査、little-endian、unaligned access、grow 後の backing storage
- block、loop、branch、関数呼び出しの値転送
- backend による置換が成立しない場合の scalar fallback

opcode ごとの C# 文字列生成は lowering 層へ移し、emitter は canonical lowering の式、代入、呼び出し、制御構造を C# へ出力する。backend は「BCL 呼び出し」「vector intrinsic」「Unity.Mathematics 呼び出し」「既存 helper の維持」「scalar fallback」のいずれかを選ぶ。選択できない操作を成功値や近似値へ置き換えない。

## 実施手順

1. [I32Operations.cs](../../src/Wasm2Cs/I32Operations.cs)、`I64Operations.cs`、`FloatOperations.cs`、`ConversionOperations.cs`、`MemoryOperations.cs` について、現在の helper、C# 演算、BCL 候補、意味差、fallback、必要 assembly を表にする。BCL の API は target profile の reference assembly で利用可否を確認する。
2. [Module.cs](../../src/Wasm2Cs/Module.cs) の型付き命令情報を入力にして、stack-machine 命令から canonical lowering への変換を追加する。[Validator.cs](../../src/Wasm2Cs/Validator.cs) の型情報と一致する単純な値の連鎖、local への代入、定数、load/store、関数呼び出しから始め、block／loop の合流規則は既存の検証結果を再解釈しない。
3. [MemoryOperations.cs](../../src/Wasm2Cs/MemoryOperations.cs) と `src/Wasm2Cs.Runtime` の memory helper を `dotnet-netstandard2.1` backend から利用できるようにし、`Span<byte>`、`ReadOnlySpan<byte>`、`MemoryMarshal`、`Array.Copy`、`Buffer.BlockCopy` などを適用する。WASM memory は little-endian なので、ホスト endian に依存する cast を無条件には使わず、必要な byte order を明示する。
4. `dotnet-vector` backend と `unity-mathematics` backend の共通インターフェースを新設する。まずは [Decoder.cs](../../src/Wasm2Cs/Decoder.cs) に全 v128 opcode を追加するのではなく、canonical vector 操作の小型 fixture で、同じ操作を `Vector128<T>` と `float4` へ変換できることを確認する。WebAssembly SIMD の opcode 対応は後続段階で行う。
5. [FloatOperations.cs](../../src/Wasm2Cs/FloatOperations.cs) の f32／f64 `Math` 呼び出し、整数の bit 操作、[MemoryOperations.cs](../../src/Wasm2Cs/MemoryOperations.cs) の memory copy などを、意味差を確認した単位から BCL に置き換える。NaN、signed zero、除算 trap、範囲検査が異なる操作は wrapper または既存 helper を残す。
6. memory の範囲付き操作では、`Span` や `MemoryMarshal` から得た view を `memory.grow` の前後で保持しない。`WasmMemory` の backing storage を長寿命の public span／array として公開せず、runtime 内の一回の load/store/copy 操作に view の寿命を閉じ込める。既存の host API はコピーを返し、grow が backing storage を交換する設計を維持する。
7. CLI、Source Generator、Unity 入力橋渡しで profile を明示的に選べるようにする。profile にない assembly の参照、未対応の intrinsic、依存 package の欠落は生成またはコンパイル時に診断する。
8. SH-08 で行う大規模 codegen とは検証を分ける。SH-05.5 では lowering の意味と target 選択を固定し、SH-08 ではその lowering を関数分割、初期化分割、巨大な制御フローへ適用する。

## 前提と未決事項

- `Transpiler.Translate` の既存単一文字列 API は維持し、profile は新しいオプションまたは別 API として追加する。[WasmGenerator.cs](../../src/Wasm2Cs.Generator/WasmGenerator.cs)、[Wasm2Cs.targets](../../build/Wasm2Cs.targets)、Unity の `WasmAssetBridge.cs` が同じ profile 名を受け取る方式は実装時に確定する。
- 生成器本体を .NET Standard 2.0 に残せるか、target-specific runtime を multi-target にするか、profile ごとの別 assembly に分けるかは、reference assembly と package 構成を確認して決める。
- `dotnet-vector` の target framework、`System.Runtime.Intrinsics` の利用可能な型、`Unity.Mathematics` の package version は未固定である。固定前に .NET と Unity の対象版、reference assembly、IL2CPP のコンパイル結果を記録する。
- `v128` の decoder／validator／opcode 対応は、この段階で定める backend 境界を利用する別 milestone として扱う。

## リスクと対策

| リスク | 対策 |
|---|---|
| BCL が NaN、signed zero、丸め、trap の意味を保たない | opcode ごとに意味差を表へ記録し、BCL 呼び出しの前後に wrapper または bit 操作を置く。差分テストを通らない置換を採用しない |
| netstandard2.0、netstandard2.1、.NET intrinsics、Unity.Mathematics の依存が生成物へ混入する | profile ごとの reference assembly と package を分け、選択していない backend の型名・assembly 名を生成 source から検査する |
| `Span`／`MemoryMarshal` が grow 前の backing storage を参照し続ける | public な長寿命 span／array を返さず、runtime helper の一操作内に view の寿命を閉じ込める。grow 後の共有 memory テストを必須にする |
| .NET と Unity の vector 型を同一の API とみなして意味差を見落とす | canonical vector 操作から各 backend が個別に変換し、lane ごとの結果、NaN、範囲外処理を scalar profile と比較する |
| CRT import の名前判定が通常の WASM 関数を誤置換する | import の置換は SH-09 の module/name/signature 対応表に限定し、内部関数 pattern は SH-08 で別に検証する |

## 検証

[共通回帰とパッケージ検証](../self-hosting-design.md) に加え、profile ごとに同じ fixture を生成・コンパイル・実行する。

- 既存の scalar profile と各最適化 profile の戻り値、trap、memory、global の状態が一致すること。
- f32／f64 の arithmetic、NaN、signed zero、reinterpret が BCL 呼び出し導入後も一致すること。
- `Span`／`MemoryMarshal` を使う memory load/store、unaligned access、little-endian、範囲外アクセスが一致すること。
- `memory.grow` 後に、生成コードと host が新しい backing storage を参照し、古い span／array を長寿命の public API として公開しないこと。
- `dotnet-netstandard2.1` の生成 C# が対応する reference assembly でコンパイルできること。
- `dotnet-vector` が対象 framework の `Vector128<T>` を参照してコンパイルできること。利用できない target では profile の診断または scalar profile への明示的 fallback になること。
- `unity-mathematics` が Unity Editor と Windows x64 IL2CPP でコンパイル・実行でき、`float4` の結果が scalar profile と一致すること。
- 選択していない backend の assembly を生成物が参照しないこと。
- lowering 前後の生成サイズ、C# コンパイル時間、実行時間、memory 使用量を同じ fixture と target version で比較すること。

## 合格条件

- [ ] canonical lowering と target backend の境界があり、既存の opcode 直書き emitter に新しい BCL／SIMD 分岐を追加し続ける構造になっていない。
- [ ] 既存 `portable-netstandard2.0` の公開 API と全回帰結果が変わらない。
- [ ] `dotnet-netstandard2.1` で `Span<T>`／`MemoryMarshal` を使う代表的な memory lowering がコンパイル・実行できる。
- [ ] `dotnet-vector` と `unity-mathematics` を明示的に切り替えられ、選択した target 以外の型・assembly が生成物へ混入しない。
- [ ] scalar と最適化 profile の結果、trap、memory/global 状態が参照実行と一致する。
- [ ] memory grow、NaN、signed zero、little-endian、範囲外アクセスの不変条件が維持される。
- [ ] canonical vector lowering の代表 fixture を両 backend で実行できる。ただし WebAssembly SIMD の全命令対応は別段階の合格条件にする。
- [ ] lower 前後の生成サイズとコンパイル時間を記録し、改善しなかった場合も結果を残す。

## 非対象・失敗時の扱い

WebAssembly SIMD の全 opcode、relaxed SIMD、CPU feature の実行時 dispatch、GPU shader 化はこの段階に含めない。全 opcode は SH-01 の inventory と対応づけた後、SH-08 の大規模 codegen との依存関係を確認して別 milestone を追加する。

`memcpy` や `sqrtf` などの import を名前だけで BCL へ置換しない。WASM 内部関数の pattern 認識は SH-08、import された CRT／runtime ABI は SH-09 の対応表と署名検証で扱う。profile の変更で unsupported instruction を成功値へ変換したり、意味差を許容誤差へ隠したりしない。

## 現在の実装

`WasmTargetProfile` と `WasmTargetProfiles` を追加し、[Transpiler.cs](../../src/Wasm2Cs/Transpiler.cs) の既存 API に profile を指定する overload を追加した。[CLI](../../src/Wasm2Cs.Cli/Program.cs) は `--target-profile`／`-p` で同じ profile 名を受け取る。`CSharpEmitter` は `LoweringPlan` と [LoweringBackend.cs](../../src/Wasm2Cs/LoweringBackend.cs) を介して memory・演算 backend を選ぶ。既存の引数なし overload は `portable-netstandard2.0` を使う。

`Wasm2Cs.Runtime` は `netstandard2.0` と `netstandard2.1` を multi-target にした。netstandard2.1 の `WasmMemory` は `Span` と `MemoryMarshal` を一つの load/store 操作内で使う typed access を提供し、生成された `dotnet-netstandard2.1` と `dotnet-vector` profile がその API を選ぶ。portable と `unity-mathematics` profile は byte access の fallback を使う。`Array.Copy` は overlap-safe な memory.copy に、netstandard2.1 の `Span.Fill` は memory.fill に使う。`LoweringBackend` は現在、f32 の `sqrt`／丸めで意味保存用wrapper付きの `MathF` を選択し、その他の演算は既存 scalar helper へ fallback する。

Source Generator は MSBuild の `Wasm2CsTargetProfile` を読み取り、`Wasm2Cs.targets` はその property を analyzer config へ公開する。Unity AdditionalFile は明示的な property がない場合に `unity-mathematics` profile を選ぶ。今回の実装では、canonical vector 操作の小型 vocabulary（f32x4 の加算・乗算）を `Vector128<float>`／`Unity.Mathematics.float4` へ選択的に変換する backend 境界と、.NET側の `Vector128` 生成式を対象reference assemblyでコンパイルするfixtureを追加した。stack-machine 全体を式・SSA へ変換する canonical IR と WebAssembly SIMD opcode の decode はまだ追加していない。
